Enterprise JFrog Migration to OpenShift

Blue-Green Deployment Strategy for Artifactory HA, Xray HA & Catalog

Migrating a running enterprise JFrog stack from VM-based architecture with Oracle RAC, LDAP, NFS, and Apache blue-green routing to a Helm-deployed OpenShift environment requires careful planning. This guide prioritizes data integrity, minimal downtime, and preservation of existing enterprise dependencies while decoupling the application layer into immutable containers.

1

Phase 1: Architecture Validation & Prerequisites

Before touching production, validate that the OpenShift cluster can consume existing external resources without performance degradation.

Network & Storage Connectivity Verification

  1. Oracle RAC: Verify connectivity from OpenShift pods to RAC VIPs. Ensure firewall rules allow traffic on Oracle listener ports (default 1521) and connection strings are resolvable from within pod network.
  2. NFS Shares: Test mount points from temporary debug pods against existing NFS storage. Validate latency and throughput; containerized I/O on NFS can behave differently than VM-mounted filesystems.
  3. LDA P: Confirm bind credentials and schema compatibility for service accounts accessing AD/LDAP from within the OpenShift namespace.

Chart & Value Mapping

  • Deploy official JFrog Helm charts (Artifactory, Xray, Platform/Catalog) in non-production staging namespace
  • Map current directories (artifacts-internal, data, logs, backup) to OpenShift Persistent Volume Claims backed by NFS storage class
  • Ensure persistence block in values.yaml points directly to existing NFS paths to preserve data continuity
Database Schema Compatibility

Run JFrog database upgrade utility against clone of Oracle RAC instance to ensure target Artifactory/Xray version supports existing schema.

2

Phase 2: Green Environment Provisioning (Parallel Deployment)

Spin up the "Green" environment on OpenShift while the "Blue" (VMs) remains live.

  1. Secret Management Injection: Convert LDAP credentials, Oracle DB passwords, and license keys into OpenShift Secrets. Configure Helm chart to reference these secrets—never hardcode values.
  2. Application Deployment (Read-Only Mode): Install Helm releases pointing to existing Oracle RAC and NFS paths. Initialize instances but keep them from writing to active transaction logs until cutover.
  3. Health Check & Warm-up:
    • Allow Green nodes to start indexing artifacts from shared NFS
    • Verify binary cache is populated and search indices are built using existing data
    • Confirm LDAP authentication flows successfully
    • Verify Oracle RAC connectivity with no lock contention from Blue VMs
Critical Warning

Since both Blue and Green share the same DB/NFS, there is risk of race conditions if both try to index or write simultaneously. Strategy relies on strictly sequential cutover.

3

Phase 3: Blue-Green Cutover Strategy

The critical path where you minimize downtime using existing Apache VHOSTs to route traffic from Blue to Green.

  1. Pre-Cut Over Freeze:
    • Announce maintenance window
    • Pause CI/CD pipelines consuming Artifacts to prevent new writes to Blue system
    • Stop Writes: Enable "Read-Only" mode on Blue VMs via Admin UI or CLI
  2. Data Synchronization Window: Since both systems share DB/NFS, sync ensures Green nodes have fully processed pending transactions left in DB by Blue nodes. Wait for Green "System Status" to report Healthy and Indexing Complete.
  3. DNS/VHOST Switch (The Switch):
    • Modify Apache VHOST configuration (or OpenShift Route/Ingress controller)
    • Update virtual host definitions to proxy traffic to Green OpenShift Service endpoints instead of Blue VM IPs
    • Ensure DNS TTLs were lowered prior to this event to prevent client-side caching delays
  4. Traffic Validation: Direct internal test users to new endpoint. Verify artifact pulls/pushes, Xray scans, and LDAP logins work correctly.
4

Phase 4: Post-Migration Stabilization & Decommissioning

  1. Write Lock Release: Once Green is confirmed stable and handling traffic, shut down Blue VMs or stop their services to prevent accidental dual-write scenarios. Remove Blue entries from Apache load balancer completely.
  2. License & Node Identity Adjustment: In some JFrog versions, node IDs are tied to hostname/IP. Verify new OpenShift pods have accepted license and report as valid nodes in Cluster UI. May need to transfer license token explicitly if hardware-bound.
  3. Cleanup: After stability confirmed for 24-48 hours:
    • Shut down and deprovision VMs
    • Remove old Apache VHOST rules pointing to VMs
    • Archive old infrastructure configurations

⚠ Critical Risk Mitigation Points

Oracle RAC Lock Contention

Since you're sharing the DB, the biggest risk is Green pods trying to write to tables Blue VMs are locking. Recommendation: Perform the "Stop Writes" phase aggressively. Do not run Blue and Green in parallel with active writes to the same DB unless extensively tested.

NFS Permissions

Containerized JFrog processes often run under specific non-root UID (e.g., `1000`). Ensure your NFS export permissions and `fsGroup` in OpenShift SecurityContextConstraints match exactly what the VM user had, otherwise you will face "Permission Denied" errors on binary store.

Xray Indexing

Moving from VM to OCP changes how Xray indexes artifacts. Ensure memory limits for Xray pods in Helm chart are sufficient to rebuild indices from massive NFS store without OOM kills.

Required Tools Summary

  • OpenShift CLI (`oc`) and Helm
  • JFrog CLI — For validation commands (check status, check connectivity)
  • Apache HTTP Server — To manage VHOST switch (or OpenShift Routes if moving LB to OCP)

This migration strategy leverages existing infrastructure investment while modernizing the compute layer. It avoids full data migration complexity by utilizing shared storage, but demands strict control over the "dual-active" period to avoid database corruption.
